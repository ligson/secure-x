# 加密与存储设计

## 1. 安全目标

- 服务端永不持有可直接解密用户数据的能力
- 网络传输中的敏感内容始终为密文
- 单个条目泄露不应影响全部数据
- 单个文件泄露不应影响其他文件

## 2. 建议密钥层次

建议采用以下分层模型：

### 2.1 主密码

- 仅由用户记忆
- 只在客户端输入和使用
- 不直接作为加密密钥使用

### 2.2 根密钥

- 由客户端基于主密码通过 `Argon2id` 派生
- 用于解开账户主数据密钥

### 2.3 账户主数据密钥

- 用于保护各类条目密钥或目录密钥
- 以密文形式保存在服务端和本地缓存中

### 2.4 条目密钥

- 每个密码条目或安全备注可使用独立数据密钥
- 降低单个条目密钥泄露带来的影响范围

### 2.5 文件密钥

- 每个文件单独生成随机密钥
- 文件密钥再由账户主数据密钥或目录密钥进行封装

## 3. 加密建议

### 3.1 文本类条目

- 算法建议：`AES-256-GCM` 或 `XChaCha20-Poly1305`
- 每个条目使用独立随机 `nonce`
- 密文字段中保留版本号与算法标识，便于后续升级

### 3.2 文件类数据

- 大文件建议分块加密
- 每块采用独立随机参数
- 服务端保存：
  - 文件密文
  - 块索引
  - 哈希校验
  - 内容长度等非敏感元数据

## 4. 服务端可见数据

服务端通常可以看见：

- 用户账号标识
- 设备标识
- 条目数量与部分结构性元数据
- 文件大小、上传时间、同步时间
- 密文与版本号

服务端不应看见：

- 密码明文
- 备注明文
- 文件原文
- 主密码
- 可直接解密的主数据密钥

## 5. 认证与密码处理建议

- 登录认证口令与加密主密码逻辑尽量分离
- 可考虑：
  - 账号登录密码用于服务端身份认证
  - 主密码用于客户端数据解密
- 如果希望简化体验，也可以用一个用户输入派生两套用途不同的密钥，但需要清晰区分协议

基于安全与演进性，建议优先采用“双密码语义”设计：

- 一个用于 `服务器认证`
- 一个用于 `本地加密`

如果首版要简化为单密码，也应在协议上分离用途，避免直接复用同一原始值。

## 6. 本地存储建议

- 敏感会话密钥尽量保存在平台安全存储中
- 本地缓存中的业务数据默认保存密文
- 仅在用户解锁会话后于内存中短暂保留解密态
- 应提供应用锁定、超时重新解锁等机制

## 7. 风险与注意事项

- 不能把“忘记主密码可恢复明文数据”作为默认能力
- 文件预览会引入临时明文文件落盘风险，需要单独设计
- 多端并发修改需要版本策略，否则容易覆盖新数据
- 搜索如果要跨端高可用，需要在“本地明文索引”和“服务端可搜索性”之间做权衡
