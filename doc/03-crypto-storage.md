# 加密与存储设计

## 1. 安全目标

- 服务端永不持有可直接解密用户数据的能力
- 网络传输中的敏感内容始终为密文
- 单个条目泄露不应影响全部数据
- 单个文件泄露不应影响其他文件

## 2. 建议密钥层次

建议采用以下分层模型：

### 2.1 解锁密码

- 仅由用户记忆
- 只在客户端输入和使用
- 不直接作为加密密钥使用

### 2.2 根密钥

- 设计建议是由客户端基于解锁密码通过 `Argon2id` 派生
- 用于解开账户主数据密钥

第一版实现说明：

- 当前 Flutter 基线优先采用了 `PBKDF2-SHA256` 派生主密钥
- 这样做是为了优先复用稳定跨平台库并尽快跑通客户端加密闭环
- 后续版本可在协议保留 `kdfAlgorithm` 字段的前提下升级为 `Argon2id`

### 2.3 账户主数据密钥

- 用于保护各类条目密钥或目录密钥
- 以密文形式保存在服务端和本地缓存中

### 2.4 条目密钥

- 每个密码条目或安全备注可使用独立数据密钥
- 降低单个条目密钥泄露带来的影响范围

### 2.5 文件密钥

- 每个文件单独生成随机密钥
- 文件密钥再由账户主数据密钥或目录密钥进行封装

## 3. 加密建议

### 3.1 文本类条目

- 算法建议：`AES-256-GCM` 或 `XChaCha20-Poly1305`
- 每个条目使用独立随机 `nonce`
- 密文字段中保留版本号与算法标识，便于后续升级

### 3.2 文件类数据

- 大文件建议分块加密
- 每块采用独立随机参数
- 服务端保存：
  - 文件密文
  - 块索引
  - 哈希校验
  - 内容长度等非敏感元数据

第一版实现补充说明：

- 密码库分类与文件目录已经拆分为两套模型
- 密码库分类只用于组织密码/登录项
- 文件模块按网盘目录语义组织，文件目录名称同样作为客户端密文元数据保存
- 文件名、文件密钥、原始大小等业务信息在客户端加密后写入服务端
- 服务端只保存目录/文件的密文元数据、密文文件体、版本号和归属关系

## 4. 服务端可见数据

服务端通常可以看见：

- 用户账号标识
- 设备标识
- 条目数量与部分结构性元数据
- 文件大小、上传时间、同步时间
- 密文与版本号

服务端不应看见：

- 密码明文
- 备注明文
- 文件原文
- 解锁密码
- 可直接解密的主数据密钥

## 5. 认证与密码处理建议

- 登录认证口令与解锁密码逻辑尽量分离
- 可考虑：
  - 账号登录密码用于服务端身份认证
  - 解锁密码用于客户端数据解密
- 如果希望简化体验，也可以用一个用户输入派生两套用途不同的密钥，但需要清晰区分协议

基于安全与演进性，建议优先采用“双密码语义”设计：

- 一个用于 `服务器认证`
- 一个用于 `本地加密`

第一版实现状态：

- 已采用“双密码语义”
- 登录密码用于服务端身份认证
- 登录用户可在设置中修改服务端登录密码，修改时需要校验当前登录密码
- 解锁密码用于客户端派生解锁密钥与解封装保险库密钥
- 修改解锁密码时，客户端必须先用当前解锁密码解封装保险库密钥，再用新解锁密码重新封装同一个保险库密钥
- 修改登录密码不会修改解锁密码，不会重新加密保险库数据，也不会让服务端接触业务明文

如果首版要简化为单密码，也应在协议上分离用途，避免直接复用同一原始值。

## 6. 本地存储建议

- 敏感会话密钥尽量保存在平台安全存储中
- 本地缓存中的业务数据默认保存密文
- 仅在用户解锁会话后于内存中短暂保留解密态
- 应提供应用锁定、超时重新解锁等机制

第一版实现补充说明：

- 当前客户端会优先把认证 token 保存到平台安全存储
- 在 macOS 本地调试场景下，如果系统 Keychain 因签名或 entitlement 原因不可用，客户端不会中断当前会话
- 在 `macOS Debug` 联调模式下，如果系统安全存储不可用，客户端会自动回退到本地调试存储以保留登录态
- 该回退仅用于本地调试便利性，不作为正式发行包的默认安全策略
- 后续若提供正式签名的桌面发行包，应恢复稳定的系统安全存储持久化能力

## 7. 风险与注意事项

- 不能把“忘记解锁密码可恢复明文数据”作为默认能力
- 文件预览会引入临时明文文件落盘风险，需要单独设计
- 多端并发修改需要版本策略，否则容易覆盖新数据
- 搜索如果要跨端高可用，需要在“本地明文索引”和“服务端可搜索性”之间做权衡
