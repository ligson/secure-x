# 加密与存储设计

## 1. 安全目标

- 系统按“超级安全”的敏感信息存储系统设计，默认安全优先于便利性
- 涉及敏感数据的传输、同步、聊天、归档、密钥封装与恢复时，默认遵循 `E2EE（端到端加密，End-to-End Encryption）` 设计边界
- 每个用户的数据只能由该用户自己的客户端在正确解锁后解密
- 其他用户、服务端、数据库管理员、文件存储管理员都不能解密看到用户业务明文
- 服务端永不持有可直接解密用户数据的能力
- 网络传输中的敏感内容始终为密文
- 单个条目泄露不应影响全部数据
- 单个文件泄露不应影响其他文件
- 升级、迁移、重建索引或切换协议时，默认不允许丢失用户已有数据；客户端本地密文、服务端密文、数据库记录和归档都必须优先兼容读取并做增量迁移

## 2. 建议密钥层次

建议采用以下分层模型：

### 2.1 解锁密码

- 仅由用户记忆
- 只在客户端输入和使用
- 不直接作为加密密钥使用

### 2.2 根密钥

- 设计建议是由客户端基于解锁密码通过 `Argon2id` 派生
- 用于解开账户主数据密钥

第一版实现说明：

- 当前 Flutter 基线优先采用了 `PBKDF2-SHA256` 派生主密钥
- 这样做是为了优先复用稳定跨平台库并尽快跑通客户端加密闭环
- 后续版本可在协议保留 `kdfAlgorithm` 字段的前提下升级为 `Argon2id`

### 2.3 账户主数据密钥

- 用于保护各类条目密钥或目录密钥
- 以密文形式保存在服务端和本地缓存中

### 2.4 条目密钥

- 每个密码条目或安全备注可使用独立数据密钥
- 降低单个条目密钥泄露带来的影响范围

### 2.5 文件密钥

- 每个文件单独生成随机密钥
- 文件密钥再由账户主数据密钥或目录密钥进行封装

## 3. 加密建议

### 3.1 文本类条目

- 算法建议：`AES-256-GCM` 或 `XChaCha20-Poly1305`
- 每个条目使用独立随机 `nonce`
- 密文字段中保留版本号与算法标识，便于后续升级

### 3.2 文件类数据

- 大文件建议分块加密
- 每块采用独立随机参数
- 服务端保存：
  - 文件密文
  - 块索引
  - 哈希校验
  - 内容长度等非敏感元数据

第一版实现补充说明：

- 密码库分类与文件目录已经拆分为两套模型
- 密码库分类只用于组织密码/登录项
- 文件模块按网盘目录语义组织，文件目录名称同样作为客户端密文元数据保存
- 文件名、文件密钥、原始大小等业务信息在客户端加密后写入服务端
- 服务端只保存目录/文件的密文元数据、密文文件体、版本号和归属关系

## 4. 服务端可见数据

服务端通常可以看见：

- 用户账号标识
- 设备标识
- 条目数量与部分结构性元数据
- 文件大小、上传时间、同步时间
- 密文与版本号

服务端不应看见：

- 密码明文
- 备注明文
- 文件原文
- 聊天消息明文
- 解锁密码
- 可直接解密的主数据密钥

## 4.1 用户隔离与所有权校验

加密保护的是“拿到密文也不能解密”，权限控制保护的是“正常情况下拿不到别人的密文”。两层都必须存在。

- 所有登录态接口都必须基于当前 token 解析出的 `user_id` 查询数据
- 列表、详情、下载、更新、删除都必须追加 `user_id = 当前用户`
- 创建或更新时传入的 `folderId`、`parentFolderId`、`uploadId` 等关联 ID 必须先确认属于当前用户
- 用户不能引用其他用户的密码分类、文件目录、上传任务或文件记录
- 当前后端已对密码分类父级、文件目录父级、密码项所属分类、文件所属目录与分片上传目录做归属校验
- 好友关系不属于数据授权模型，不能绕过个人资源所有权校验；好友只能看到通讯录所需的公开账号信息
- 聊天关系必须建立在已同意的好友关系之上，但好友关系本身仍不授予任何密码库或文件访问权
- 如果未来加入分享、团队空间或组织保险库，必须显式引入授权模型与密钥共享协议，不能复用个人空间的隐式访问规则

## 4.2 聊天消息存储边界

- 聊天消息属于敏感数据，不能把可解密正文直接落服务端作为普通离线消息
- 图文聊天当前默认通过 WebSocket + 应用层端到端加密信封发送；语音/视频通话媒体链路采用自托管 LiveKit，呼叫信令仍走端到端加密实时信令，secure-x 服务端只签发短期入房 token，不保存通话媒体内容
- 当前实现把协议层抽象为 `ChatProtocol`；默认 `securex-e2ee-v1` 为每个设备维护长期身份种子和公钥目录，发送时按接收设备逐个做 ECDH，并用 AES-GCM 封装消息体
- 图片、语音、视频和文件类聊天附件不再直接塞进实时消息大包；客户端会先生成随机附件密钥并加密附件二进制，再把密文对象上传服务端，聊天消息里只放附件对象标识、大小、类型和端到端加密后的解密参数
- 服务端聊天附件接口只保存不可解密密文，并按上传者和允许接收用户做下载授权；拿到服务端文件存储或数据库的管理员仍不能解密附件内容
- 服务端最多提供实时配置、在线状态、设备公钥目录、在线密文中继、“待拉取的设备密文信封”以及“每个用户自己的加密聊天归档”，不保存消息正文，也不持有会话密钥
- 当接收方在线时，服务端只发送“有待拉取密文”的通知；当接收方暂时离线时，服务端也只能短暂保存不可解密的设备密文信封，等待接收设备上线主动拉取
- 发送方完全离线或无法访问服务端时，待发消息仍只加密保存在发送方本机缓存；一旦客户端重新联网，应自动补发到服务端的密文队列并回写用户自己的加密聊天归档
- 当前客户端本地使用应用支持目录保存聊天密文缓存，解锁后才可读取；但缓存不再是唯一历史来源
- 当前本地聊天缓存已拆成“两层密文结构”：先保存会话摘要清单，再把单个会话详情拆到独立密文文件中；聊天页进入、历史同步、送达回执和待发补发时才按需加载详情，以降低移动端内存压力
- 当前已增加用户级加密聊天归档：客户端会把自己的聊天快照再次用保险库密钥加密后同步到服务端，作为同账号多端恢复和主同步存储；服务端与其他用户都不能解密
- 当前聊天归档格式已开始从“整包密文快照”演进到“按会话分段的加密归档清单 + 会话详情”模型：新客户端优先按会话增量拉取和回写，旧整包快照继续兼容读取并作为迁移兜底，避免升级时丢失历史
- 本地缓存结构升级同样遵循兼容迁移原则：旧版整包密文快照仍可被新客户端自动读取，再平滑回写成“摘要 + 详情”两层格式，避免升级过程中丢失聊天记录
- 登录解锁后客户端会优先解密服务端聊天归档恢复历史，再通过端到端实时通道向在线好友或共同群成员请求增量历史消息；历史响应来自对方当前账号已解锁的聊天视图导出，再由实时会话密钥加密传输
- 历史同步仍只能在客户端之间发生；服务端可以保存用户自己的加密聊天归档和设备密文信封，但不得保存可解密历史消息，也不得接触可解密内容
- 群聊当前采用成员逐个投递模型：客户端为每个群成员设备逐个发送端到端密文，群会话元数据与消息快照会同步到每个成员自己的加密群聊归档中
- 当前已引入“服务端最小群元数据”模型：服务端可保存群房间、群成员关系、群管理以及每个用户各自的加密群快照，用于多端恢复群列表；这些快照只能由对应用户自己的客户端解锁后解密，服务端仍不能读取聊天明文
- 为适配手机网络，客户端应在应用回到前台、网络从无到有、Wi‑Fi 与蜂窝网络切换后自动重建实时通道；这属于连接恢复策略，不改变“服务端不可解密、只可短暂保存不可解密密文信封”的安全边界
- 当手机锁屏或弱网导致用户短暂离线时，未投递消息仍优先保存在发送方本机缓存；用户重新上线后，客户端应自动重连、补发尚未同步的消息，并拉取属于当前设备的未处理密文信封
- 用户退出群聊时必须删除当前账号本机缓存与服务端归档中的该群会话元数据和消息快照；群管理退出会把管理权转交给下一位成员，并通过端到端控制消息尽量通知在线成员
- 群聊成员变更必须继续遵守“服务端不可解密”原则；后续补全群历史同步、成员移除后的密钥轮换和上线向在线成员拉取历史时，需要独立群密钥协议
- 当前多设备聊天同步优先采用“用户自己的加密聊天归档”方案；若后续要升级成真正的跨设备逐条消息同步、长时离线投递或更复杂的群协议，必须继续引入更明确的设备密钥、消息密钥、协议版本与显式迁移机制，不能直接把明文或可解密密文托管给服务端

## 5. 认证与密码处理建议

- 登录认证口令与解锁密码逻辑尽量分离
- 可考虑：
  - 账号登录密码用于服务端身份认证
  - 解锁密码用于客户端数据解密
- 如果希望简化体验，也可以用一个用户输入派生两套用途不同的密钥，但需要清晰区分协议

基于安全与演进性，建议优先采用“双密码语义”设计：

- 一个用于 `服务器认证`
- 一个用于 `本地加密`

第一版实现状态：

- 已采用“双密码语义”
- 登录密码用于服务端身份认证
- 登录用户可在设置中修改服务端登录密码，修改时需要校验当前登录密码
- 解锁密码用于客户端派生解锁密钥与解封装保险库密钥
- 修改解锁密码时，客户端必须先用当前解锁密码解封装保险库密钥，再用新解锁密码重新封装同一个保险库密钥
- 修改登录密码不会修改解锁密码，不会重新加密保险库数据，也不会让服务端接触业务明文

如果首版要简化为单密码，也应在协议上分离用途，避免直接复用同一原始值。

## 6. 本地存储建议

- 敏感会话密钥尽量保存在平台安全存储中
- 本地缓存中的业务数据默认保存密文
- 仅在用户解锁会话后于内存中短暂保留解密态
- 应提供应用锁定、超时重新解锁等机制

第一版实现补充说明：

- 当前客户端会优先把认证 token 保存到平台安全存储
- 在 macOS 本地调试场景下，如果系统 Keychain 因签名或 entitlement 原因不可用，客户端不会中断当前会话
- 在 `macOS Debug` 联调模式下，如果系统安全存储不可用，客户端会自动回退到本地调试存储以保留登录态
- 该回退仅用于本地调试便利性，不作为正式发行包的默认安全策略
- 后续若提供正式签名的桌面发行包，应恢复稳定的系统安全存储持久化能力

## 7. 风险与注意事项

- 不能把“忘记解锁密码可恢复明文数据”作为默认能力
- 文件预览会引入临时明文文件落盘风险，需要单独设计
- 多端并发修改需要版本策略，否则容易覆盖新数据
- 搜索如果要跨端高可用，需要在“本地明文索引”和“服务端可搜索性”之间做权衡
