# 架构设计

## 1. 总体架构

建议采用“单后端服务 + Flutter 多端客户端”的结构。

### 1.1 客户端职责

- 用户注册与登录界面
- 解锁密码输入与本地密钥派生
- 数据项加密与解密
- 文件分块加密与解密
- 聊天加密归档、本地缓存与实时通道状态
- 好友通讯录、好友申请与好友详情展示
- 本地缓存与离线读取
- 后端地址配置
- 随机密码生成

### 1.2 服务端职责

- 用户注册、登录态与访问令牌管理
- 密文条目元数据存储
- 密文文件存储
- 好友关系与好友申请状态存储
- 实时服务配置、在线状态、设备目录、待拉取密文队列与在线密文中继
- 数据版本与同步接口
- 基础审计与异常记录

### 1.3 存储职责

- `SQLite`：保存用户、设备、会话、条目索引、文件索引、版本信息
- 文件存储目录：保存加密后的文件二进制对象

## 2. 建议模块拆分

### 2.1 Flutter 客户端

- `app_shell`
  - 平台入口、路由、主题、配置
- `auth`
  - 注册、登录、设备认证、会话管理
- `vault`
  - 密码库分类、条目列表、详情页、搜索
- `files`
  - 文件目录、文件选择、上传、下载、解密、预览入口
- `chat`
  - 会话列表、聊天详情、服务端加密聊天归档、本地聊天缓存、实时通道状态、移动网络自动恢复
- `friends`
  - 好友列表、好友申请、添加好友、好友详情
- `groups`
  - 群聊列表、我创建的群、我加入的群、群设置、群成员管理、当前用户群快照同步
- `crypto`
  - 密钥派生、加密解密、随机数、签名校验
- `sync`
  - 拉取、推送、冲突处理、增量同步
- `local_storage`
  - 本地数据库、安全存储、缓存管理

当前实现中的 Flutter 组织约定：

- `main.dart` 只保留应用入口、根组件与主导航状态
- `src/features/auth/` 放登录、注册、解锁等认证相关页面
- `src/features/vault/` 放密码库、生成器、文件页、编辑/详情页与页面级 helper
- `src/features/chat/` 放聊天会话列表、聊天详情与输入区
- `src/features/friends/` 放好友通讯录、好友申请、添加好友与好友详情页面
- `src/features/settings/` 放设置入口、安全设置、主题卡片和设置通用组件
- `src/app_controller*.dart` 按认证、保险库、上传、记录操作、会话和内部工具拆分控制器逻辑
- 单个文件持续变大时应优先按页面、职责或领域继续拆分，避免重新形成难维护的大文件

### 2.2 Go 服务端

- `api`
  - HTTP/gRPC 接口层
- `auth`
  - 注册、登录、令牌、设备管理
- `vault`
  - 条目元数据、密码分类、版本管理
- `file_store`
  - 文件目录、文件上传下载、分块、校验
- `friends`
  - 好友申请、好友关系、公开用户信息查询
- `groups`
  - 群聊房间元数据、群成员关系、当前用户群快照与群权限校验
- `realtime`
  - 实时服务配置、在线状态、WebSocket 在线密文转发与端到端会话建立
- `repository`
  - SQLite 访问层
- `audit`
  - 安全日志、错误日志、请求追踪

当前实现中的 Go 后端组织约定：

- `internal/httpapi/router.go` 只负责组装路由与依赖
- `auth_handlers.go`、`category_handlers.go`、`item_handlers.go`、`file_handlers.go`、`upload_handlers.go`、`friend_handlers.go`、`realtime_handlers.go`、`sync_handlers.go` 按接口领域拆分 handler
- `requests.go` 放请求结构，`helpers.go` 放参数、认证和文件读写辅助逻辑
- 新增 HTTP 接口时优先延续领域拆分，不把业务处理重新堆回 `router.go`

## 3. 建议交互流程

### 3.1 注册

1. 客户端输入账号信息与解锁密码
2. 客户端基于解锁密码派生根密钥
3. 客户端生成用于保护数据密钥的密钥材料
4. 服务端保存账号、认证相关材料与密文配置

### 3.2 登录

1. 用户输入后端地址、账号和登录密码
2. 客户端与服务端完成身份认证
3. 客户端进入解锁页，使用解锁密码恢复本地所需密钥
4. 客户端拉取密文数据并在本地解密展示

### 3.3 条目同步

1. 客户端本地修改条目
2. 客户端重新加密该条目
3. 客户端上传密文与版本号
4. 服务端只记录密文与版本变化

### 3.4 文件上传

1. 客户端读取本地文件
2. 客户端生成文件密钥并按分片加密文件
3. 客户端以后台任务上传密文分片并显示进度
4. 服务端记录上传会话、接收密文分片并在完成后合并
5. 客户端上传密文元数据，服务端保存对象并记录索引

当前实现支持应用内后台分片上传和服务端合并；后续需要继续补齐客户端持久化上传任务，以支持应用重启后的自动断点恢复。

### 3.5 好友申请

1. 用户通过准确用户名或邮箱发送好友申请
2. 服务端只记录申请双方、状态和申请说明，不读取任何保险库数据
3. 被申请方同意后，服务端建立双向好友关系
4. 好友关系只影响通讯录展示，不影响密码库、文件库、同步导出或密文下载的所有权校验
5. 删除好友只删除关系，不删除双方各自的密文数据
6. 好友关系变化会通过实时通道通知在线客户端刷新好友与申请快照，避免申请方长时间停留在旧状态

### 3.6 加密聊天

1. 客户端通过 HTTP 接口读取实时服务配置，包括信令地址、传输类型与可选 ICE 信息
2. 客户端使用登录 token 建立 WebSocket 实时连接，并在 query 中携带当前设备标识；服务端校验身份与好友/共同群成员关系后只负责 presence、待拉取通知和密文信封在线转发
3. 图文聊天当前默认使用 `WebSocket + 应用层端到端加密` 主链路；后续如果增加语音视频通话，再单独引入 WebRTC
4. 聊天协议层必须接口化。当前以 `ChatProtocol` 抽象实现 `securex-e2ee-v1`，后续可以替换为更强的设备协商或群协议，而不直接绑死在当前实现
5. 每个用户设备持有自己的长期身份种子和公钥目录；发送方按接收用户的每个设备逐个做 ECDH，再用 AES-GCM 封装聊天正文
6. 服务端不保存可解密聊天正文、不参与解密，也不持有会话密钥；服务端只看到设备公钥目录、不可解密密文信封和每个用户自己的加密聊天归档
7. 当接收方在线时，服务端通过 WebSocket 通知“有待拉取密文”；当接收方暂时离线时，服务端也只能短暂保存不可解密的设备密文信封，等待接收设备下次上线主动拉取
8. 客户端解锁后优先加载服务端加密聊天归档恢复会话；Flutter 跨平台应用支持目录中的本地聊天快照仍会保留，但角色降级为性能缓存与故障兜底
9. 当前本地聊天缓存也采用“两层密文结构”：先加载按会话摘要组成的轻量清单，再在用户进入某个聊天页、历史同步或消息补发前按需解密该会话详情，减少手机端首屏卡顿和大对象常驻内存
10. 当前聊天归档在服务端支持“整包密文快照”和“按会话分段的加密归档清单 + 详情”两层结构：新客户端优先读取增量清单，只拉取变更过的会话详情；旧整包归档继续保留为兼容读取和迁移兜底
11. 实时消息发送后先显示已发送，接收端成功解密并处理后，会再发送端到端加密的投递回执，发送方收到后显示已送达
12. 登录解锁后客户端自动注册当前设备、公钥和协议版本，建立实时连接，并主动拉取属于当前设备的待同步密文信封
13. 登录解锁后客户端还会自动向在线好友或共同群成员发起端到端历史同步；历史请求与响应同样走设备级 E2EE 信封
14. 历史同步按消息 ID 去重并转换发送方视角；同账号多设备优先通过“用户自己的加密聊天归档”恢复，跨用户历史同步主要作为在线增量对账与补漏链路
15. 群聊按群成员设备逐个端到端加密投递；服务端保存群房间、群管理、成员关系，以及“当前用户自己的加密群快照”，用于多端恢复群列表、成员关系和已归档历史，但这些快照不包含可供服务端解密的聊天明文
16. 群设置支持退出群聊；退出者需要同步删除本机缓存和自己在服务端加密归档中的该群会话与聊天记录，群管理退出时按成员顺序自动升级下一位成员为群管理，并通过端到端控制消息通知在线成员
17. 群成员删除、邀请与历史可见性后续必须补充群密钥轮换设计，不能依赖服务端保存可解密消息
18. 为适配手机网络，客户端需要在应用回到前台、Wi‑Fi/蜂窝切换、弱网恢复后强制重连 WebSocket，并重新触发待同步消息上云、待拉取密文拉取、聊天归档同步与历史同步
19. 实时信令授权不能只看好友关系；若两个用户存在共同群聊，也应允许他们建立端到端会话或走在线密文中继，但依然不能借此访问对方保险库和文件密文
20. 聊天相关的本地结构、密文载荷和服务端表都必须带版本或协议标识；升级只能做增量迁移，不能因为协议迭代导致用户本地聊天数据、服务端密文队列或归档丢失

## 3.7 统一接口响应

后端 JSON 接口统一采用以下响应包裹结构：

```json
{
  "success": true,
  "message": "",
  "httpCode": 200,
  "data": {}
}
```

设计要求：

- `success` 反映业务处理是否成功
- `message` 为前端可直接消费的显示信息
- `httpCode` 必须与真实 HTTP 状态码一致
- `data` 承载具体业务数据，没有数据时返回空对象
- 不再混用裸对象、空响应体、字符串错误等多种返回风格

## 4. 建议目录结构

后续实现时建议采用如下仓库布局：

```text
secure-x/
  README.md
  AGENTS.md
  CHANGELOG.md
  doc/
  securex-app/
  securex-be/
    cmd/
    internal/
    pkg/
    data/
  scripts/
  deploy/
```

其中：

- `securex-app/` 用于放置 Flutter 跨平台客户端工程
- `securex-be/` 用于放置 Go 后端工程

## 5. 技术选型建议

### 5.1 服务端

- `Go 1.24+`
- Web 框架可选：`Gin` 或 `Fiber`
- 数据访问建议先从标准库 + `sqlc` 或轻量 ORM 开始
- 文件存储初期使用本地目录，后续可抽象为对象存储接口

### 5.2 客户端

- `Flutter stable`
- 状态管理建议选一个简单稳定方案，例如 `Riverpod`
- 本地数据库建议 `SQLite`
- 敏感密钥优先接入平台安全存储能力

## 6. 架构原则

- 服务端尽量无状态，方便自部署与迁移
- 认证与密文存储分离考虑，但初期可以单服务落地
- 数据结构从一开始就考虑版本号，降低后续同步改造成本
- 涉及敏感数据同步、聊天、归档、密钥封装时，默认按 `E2EE（端到端加密）` 边界设计，服务端只保留不可解密密文和最小必要元数据
- 客户端本地快照、服务端数据库、文件密文、密文队列、聊天归档和群元数据都必须优先采用兼容读取和增量迁移；不允许因为升级、协议切换或迁移脚本导致用户已有数据丢失
