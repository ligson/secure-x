# 架构设计

## 1. 总体架构

建议采用“单后端服务 + Flutter 多端客户端”的结构。

### 1.1 客户端职责

- 用户注册与登录界面
- 主密码输入与本地密钥派生
- 数据项加密与解密
- 文件分块加密与解密
- 本地缓存与离线读取
- 后端地址配置
- 随机密码生成

### 1.2 服务端职责

- 用户注册、登录态与访问令牌管理
- 密文条目元数据存储
- 密文文件存储
- 数据版本与同步接口
- 基础审计与异常记录

### 1.3 存储职责

- `SQLite`：保存用户、设备、会话、条目索引、文件索引、版本信息
- 文件存储目录：保存加密后的文件二进制对象

## 2. 建议模块拆分

### 2.1 Flutter 客户端

- `app_shell`
  - 平台入口、路由、主题、配置
- `auth`
  - 注册、登录、设备认证、会话管理
- `vault`
  - 文件夹、条目列表、详情页、搜索
- `files`
  - 文件选择、上传、下载、解密、预览入口
- `crypto`
  - 密钥派生、加密解密、随机数、签名校验
- `sync`
  - 拉取、推送、冲突处理、增量同步
- `local_storage`
  - 本地数据库、安全存储、缓存管理

### 2.2 Go 服务端

- `api`
  - HTTP/gRPC 接口层
- `auth`
  - 注册、登录、令牌、设备管理
- `vault`
  - 条目元数据、文件夹、版本管理
- `file_store`
  - 文件上传下载、分块、校验
- `repository`
  - SQLite 访问层
- `audit`
  - 安全日志、错误日志、请求追踪

## 3. 建议交互流程

### 3.1 注册

1. 客户端输入账号信息与主密码
2. 客户端基于主密码派生根密钥
3. 客户端生成用于保护数据密钥的密钥材料
4. 服务端保存账号、认证相关材料与密文配置

### 3.2 登录

1. 用户输入后端地址、账号和主密码
2. 客户端与服务端完成身份认证
3. 客户端使用主密码恢复本地所需密钥
4. 客户端拉取密文数据并在本地解密展示

### 3.3 条目同步

1. 客户端本地修改条目
2. 客户端重新加密该条目
3. 客户端上传密文与版本号
4. 服务端只记录密文与版本变化

### 3.4 文件上传

1. 客户端读取本地文件
2. 客户端生成文件密钥并加密文件
3. 客户端上传密文文件和密文元数据
4. 服务端保存对象并记录索引

## 3.5 统一接口响应

后端 JSON 接口统一采用以下响应包裹结构：

```json
{
  "success": true,
  "message": "",
  "httpCode": 200,
  "data": {}
}
```

设计要求：

- `success` 反映业务处理是否成功
- `message` 为前端可直接消费的显示信息
- `httpCode` 必须与真实 HTTP 状态码一致
- `data` 承载具体业务数据，没有数据时返回空对象
- 不再混用裸对象、空响应体、字符串错误等多种返回风格

## 4. 建议目录结构

后续实现时建议采用如下仓库布局：

```text
secure-x/
  README.md
  AGENTS.md
  CHANGELOG.md
  doc/
  securex-app/
  securex-be/
    cmd/
    internal/
    pkg/
    data/
  scripts/
  deploy/
```

其中：

- `securex-app/` 用于放置 Flutter 跨平台客户端工程
- `securex-be/` 用于放置 Go 后端工程

## 5. 技术选型建议

### 5.1 服务端

- `Go 1.24+`
- Web 框架可选：`Gin` 或 `Fiber`
- 数据访问建议先从标准库 + `sqlc` 或轻量 ORM 开始
- 文件存储初期使用本地目录，后续可抽象为对象存储接口

### 5.2 客户端

- `Flutter stable`
- 状态管理建议选一个简单稳定方案，例如 `Riverpod`
- 本地数据库建议 `SQLite`
- 敏感密钥优先接入平台安全存储能力

## 6. 架构原则

- 服务端尽量无状态，方便自部署与迁移
- 认证与密文存储分离考虑，但初期可以单服务落地
- 数据结构从一开始就考虑版本号，降低后续同步改造成本
